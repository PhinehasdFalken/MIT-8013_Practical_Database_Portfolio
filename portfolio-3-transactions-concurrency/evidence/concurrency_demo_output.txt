S5  ISOLATION: dirty read? non-repeatable read? (price change during a customer's checkout)
==============================================================================
-- (a) READ COMMITTED (PostgreSQL default)
[t+ 0.00s] A | BEGIN
[t+ 0.00s] A | UPDATE product_variant SET unit_price = unit_price + 5000 WHERE sku = 'FK-027-44-WHI'   -- not committed yet
[t+ 0.00s] B | BEGIN
[t+ 0.01s] B | SELECT unit_price FROM product_variant WHERE sku = 'FK-027-44-WHI'   -- B does NOT see A's uncommitted price -> no dirty read
          B |   -> [(Decimal('77400.00'),)]
[t+ 0.01s] A | COMMIT
[t+ 0.01s] B | SELECT unit_price FROM product_variant WHERE sku = 'FK-027-44-WHI'   -- same query, same transaction, NEW value -> non-repeatable read
          B |   -> [(Decimal('82400.00'),)]
[t+ 0.01s] B | COMMIT
-- (b) REPEATABLE READ
[t+ 0.01s] B | BEGIN ISOLATION LEVEL REPEATABLE READ
[t+ 0.01s] B | SELECT unit_price FROM product_variant WHERE sku = 'FK-027-44-WHI'   -- B's snapshot is taken here
          B |   -> [(Decimal('82400.00'),)]
[t+ 0.02s] A | BEGIN
[t+ 0.02s] A | UPDATE product_variant SET unit_price = unit_price - 5000 WHERE sku = 'FK-027-44-WHI'   -- price restored
[t+ 0.02s] A | COMMIT
[t+ 0.02s] B | SELECT unit_price FROM product_variant WHERE sku = 'FK-027-44-WHI'   -- still the snapshot value -> checkout total stays consistent
          B |   -> [(Decimal('82400.00'),)]
[t+ 0.03s] B | COMMIT
[t+ 0.03s] B | SELECT unit_price FROM product_variant WHERE sku = 'FK-027-44-WHI'   -- new transaction sees the committed price
          B |   -> [(Decimal('77400.00'),)]

S6  DEADLOCK: two 2-pair orders lock the same two variants in opposite order
==============================================================================
[t+ 0.00s] A | BEGIN
[t+ 0.00s] B | BEGIN
[t+ 0.01s] A | UPDATE product_variant SET stock_qty = stock_qty - 1 WHERE sku = 'FK-087-44-BUR'   -- A locks X
[t+ 0.01s] B | UPDATE product_variant SET stock_qty = stock_qty - 1 WHERE sku = 'FK-047-43-WHI'   -- B locks Y
[t+ 0.01s] A | UPDATE product_variant SET stock_qty = stock_qty - 1 WHERE sku = 'FK-047-43-WHI'   -- A wants Y (held by B) ...
[t+ 1.21s] B | UPDATE product_variant SET stock_qty = stock_qty - 1 WHERE sku = 'FK-087-44-BUR'   -- B wants X (held by A) -> cycle
          B |   !! DeadlockDetected: deadlock detected
=> PostgreSQL detected the cycle and aborted session B; session A could continue.
[t+ 2.41s] B | ROLLBACK
[t+ 2.42s] A | ROLLBACK   -- (demo only – nothing is kept)

-- Fix: every transaction locks its variants in the SAME order (ascending variant_id)
[t+ 2.42s] A | BEGIN
[t+ 2.42s] A | SELECT variant_id, sku FROM product_variant WHERE sku IN ('FK-087-44-BUR', 'FK-047-43-WHI') ORDER BY variant_id FOR UPDATE   -- A locks both, lowest id first
          A |   -> [(1316, 'FK-047-43-WHI'), (1716, 'FK-087-44-BUR')]
[t+ 2.42s] B | BEGIN
[t+ 2.43s] B | SELECT variant_id, sku FROM product_variant WHERE sku IN ('FK-047-43-WHI', 'FK-087-44-BUR') ORDER BY variant_id FOR UPDATE   -- B asks in the same order -> simply waits, no cycle
          OBSERVER | session B: state=active, waiting on Lock/transactionid, blocked by pid [12556] (session A pid = 12556)
[t+ 3.63s] A | ROLLBACK   -- A finishes (demo: nothing kept)
          B |   -> [(1316, 'FK-047-43-WHI'), (1716, 'FK-087-44-BUR')]
[t+ 3.63s] B | ROLLBACK
=> With a consistent lock order the second transaction waits instead of deadlocking.
